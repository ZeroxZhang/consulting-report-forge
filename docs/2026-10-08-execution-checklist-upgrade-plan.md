# 强制执行计划与 Checklist 升级方案

日期：2026-10-08。基线：运行时 1.6.0，Git `9939db4`。

状态：本方案已完成实施，1.7.0 新建默认启用执行清单。下文保留设计阶段的原始论证与拟议措辞；实际命令、验证范围及实现边界以[执行协议](../references/execution-checklist.md)和[验证记录](2026-10-08-execution-checklist-validation.md)为准。

## 1. 真实目标与建议

用户要增加的是一份持续有效的工作计划：主 Agent 能在执行、委派、返工、会话交接和上下文压缩后，从持久记录中恢复目标、已完成事项、当前工作、阻塞原因及下一步；技能要求和用户明确要求不会随着执行变长而遗漏。

这包含四项能力：

1. **可执行的规划**：把目标拆成有输入、依赖、产物和完成条件的工作单元。
2. **可恢复的进度**：执行状态、委派和重要取舍及时写盘，不依赖聊天记忆。
3. **必须落实的要求**：图表多样性、版式多样性等要求进入必做任务，并关联本轮证据。
4. **可核实的完成**：文件存在、任务打勾、子 Agent 宣称完成，都不能单独成为验收依据。

建议增加独立的 `execution-plan.json`，复用现有蓝图、生产工具和审查链。主 Agent 负责更新计划；工具核实结构、依赖、版本和完成证据；进度视图由同一计划及现有产物派生。

完成本升级后，Agent 应当能回答：**当前目标是什么；哪些工作已经有效完成；正在做什么；什么被阻塞；哪些结果待接收；下一步可以做什么；正式交付还差什么。**

## 2. 对原始设想的修正

### 2.1 用可判断的启动条件替代“完全了解”

研究任务在开始时通常无法完全知道答案、页数和最终表达。“完全了解需求、完全知道报告怎么做”如果成为前置条件，计划可能迟迟不建立。

推荐两步创建：

- `init` 建立持久骨架，允许目标和路线仍在澄清。
- 读者、核心问题、范围、交付物、主要约束和下一阶段路线明确后，激活执行计划；此时可以存在已登记的未知和条件分支。

激活必须早于首项实质研究、计算建模、页面生产或子 Agent 委派。初步读取材料、识别文件及必要澄清可以先进行。对于范围本就清楚的任务，直接激活，不新增用户审批。

### 2.2 固定必需检查，动态细化业务任务

统一固定的是“不能遗漏的要求与关口”。具体研究问题、模型、页面和返工任务应随材料逐步细化。开始某阶段前，将该阶段拆到能独立执行和验收；远期保留阶段级任务即可。

不要求提前生成数百个小任务，也不把每次搜索、每次工具调用和每个样式属性都变成待办。

### 2.3 自主恢复有明确能力边界

本机制能提供可恢复状态和下一步建议。宿主是否保留子 Agent、是否支持查询进程、是否能恢复一个会话，仍取决于实际工具。不能承诺任何宿主都能自动复活旧执行者。

同样，工具可以核实“图表多样性已被实际审查并留下当前证据”，不能机械证明所有可能的图型都已被穷尽。判断质量仍需要主笔和必要的独立审查者负责。

## 3. 已有基础与结构性缺口

| 当前机制 | 已有价值 | 本次需要补齐的部分 |
|---|---|---|
| `analysis.brief/issues/workItems/gaps` | 问题拆解、分析状态、缺口与依赖 | 覆盖制作、委派、返工、交付的执行计划 |
| `report status/next` | 核对任务、蓝图、前置审查、pages、acceptance、最终审查 | 当前工作、待接收成果、可执行队列、恢复摘要 |
| `.forge/runs` 与任务锁 | 操作隔离、失败记录、成功产物原子发布 | 认知工作和委派的状态；防止旧上下文覆盖新进度 |
| `review-pack` | 审查草稿、告警处置、部分策略检查清单 | 从规划阶段就覆盖必做要求，接到实际成稿证据 |
| 审查快照与复用 | 保存已完成审查，识别视觉证据变化 | 进行中任务的恢复，以及执行计划的归档 |
| 多样性规则 | 已明确要求主动探索适配图型与布局 | 确保规划、代表页、最终审查都真正执行且可以追踪 |

根因是现有记录分别回答“分析是否完成”“产物是否有效”“审查是否通过”，没有一个入口把它们接成正在执行的工作计划。

源码约束也决定了实现方式：

- `analysis_projection.project()` 将整个 `doc.analysis` 纳入分析摘要。把制作待办放进去，会让普通状态更新触发分析重审。
- `audit_evidence.manifest()` 将 task 中除少数字段外的内容纳入整册公共依赖。将计划版本或状态放进 task，会扩大视觉失效范围。
- `review_contract.taskRecords()` 枚举的是已签产物依赖。把持续变化的计划放进该列表，会使过去的审查依赖今天的待办状态。
- `report_status.inspect()` 只读指定文件，不扫描目录；`latest-*` 是便利索引，不是完成证明。

因此，新增执行状态应独立存储，通过引用连接上述记录。

## 4. 权威边界与文件结构

### 4.1 一种信息只维护一个权威来源

| 信息 | 权威位置 | Checklist 如何使用 |
|---|---|---|
| 任务模式、风险、画幅、输出合同 | `task.json` | 引用、判断任务适用性 |
| 业务问题、主张、数字、来源、页面意图和图表布局选择 | `deck-blueprint.json` | 引用对象 ID，不复制内容或第二套选型表 |
| 既有分析工作项和缺口状态 | `analysis.workItems/gaps` | 映射成进度视图，不另存可冲突的完成状态 |
| 非分析工作的安排、依赖、委派、接收和返工 | `execution-plan.json` | 在这里维护 |
| 工程与实际审查证据 | audit、analysis-review、final review 等原记录 | 核实引用和版本，不能由勾选替代 |
| 面向用户和恢复会话的进度摘要 | 派生 `progress.md` 或 CLI 输出 | 可重新生成，不作为状态真源 |

### 4.2 推荐目录

```text
报告任务/
  task.json
  deck-blueprint.json
  execution-plan.json          当前执行计划，唯一可更新的计划入口
  progress.md                  派生的人类可读视图
  .forge/
    runs/                      复用现有操作与失败记录
    execution/revisions/       已发布计划的历史版本
    execution/receipts/         版本化操作回执
    execution/assignments/      持久委派说明与返回记录
```

只有在实际委派、修改或交付时才创建相应文件。内部材料不默认加入对外交付 HTML/PDF。

任务配置只新增稳定绑定：

```json
{
  "executionPlan": {
    "id": "本任务生成的稳定唯一标识",
    "record": "execution-plan.json"
  }
}
```

此字段不存 `revision`、计划文件摘要或任务状态。计划修订时不反复改写 task、HTML、audit 和 review。

装配和派生 task 需正确回绑 `record` 的相对路径。计算视觉公共依赖时，仅保留该字段中的稳定 `id`，排除 locator；工作流策略身份仍进入依赖。移动目录或更新待办不会被当成画面变化。

计划还需记录 `productionRefs`，引用本轮成功发布的 compile 结果、派生 task、HTML、audit 和聚合 review 的运行记录。当前 `compile` 返回派生 task，原 task 不会被改成指向最新 pages；恢复工具不能只读原 task 就认定最新编译丢失，也不能扫描目录后随便挑一个最新文件。每条引用需核对同一计划 ID、原任务归属、实际输入版本和成功回执。输入已变更时保留历史定位，但将对应产物标为过期；新编译成功后按依赖标记旧下游产物过期，失败的新运行不能替换上一有效链。直接运行底层命令的结果通过显式接收操作登记，未经登记不能悄然冒充当前生产版本。

## 5. 计划模型与状态语义

### 5.1 最小记录

计划级信息：schema 版本、稳定 ID、递增 revision、任务绑定、当前范围版本、创建/更新时间、激活状态、任务集合、需求引用、重要执行决策和可选当前工作提示。

每个任务至少包含：

| 字段 | 用途 |
|---|---|
| `id`、`title`、`phase` | 稳定身份、要完成的工作及所属阶段 |
| `dependsOn` | 本项开始所需的前置任务；验证不存在循环 |
| `scopeRefs` / `inputRefs` | 对应问题、工作项、页面、文件或其他对象 |
| `requirementRefs` | 本项落实哪些必需或用户要求 |
| `completionCriteria` | 怎样才算做完，使用规则 ID 或具体可检查条件 |
| `source` 或 `state` | 从原记录派生状态，或者维护新增执行状态；两者互斥 |
| `evidenceRefs` | 成果、核验或审查记录及其版本定位 |
| `assignment`（按需） | 执行者、尝试 ID、输入版本、输出位置和接收状态 |

例如分析任务引用 `analysis.workItems/<稳定ID>`，不另写一份 `complete`；页面制作和代表页预览则使用计划自己的执行状态。脚本每次查询计算统一的 `effectiveState`。

`currentFocus` 只用于提示主笔意图，不能覆盖依赖、缺口或真实产物检查。计划中保留重要的执行取舍、用户纠正和已否决路径，防止恢复后重复提出；业务结论仍写回蓝图。

### 5.2 新增执行任务的状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `pending` | 待执行 | 已登记；不代表前置依赖已满足 |
| `in_progress` | 已开始 | 依赖可用，记录执行者或本轮尝试 |
| `submitted` | 成果待接收 | 结果和实际输入版本已提交，尚未核实完成条件 |
| `done` | 本轮完成已被接受 | 证据有效、完成条件满足、所需审查完成 |
| `blocked` | 当前无法继续 | 记录具体阻塞及关联缺口/任务 |
| `cancelled` | 因范围调整取消或被替代 | 保留原因、来源与替代关系；不算完成 |

由读取器计算 `needs_revalidation`、`status_unknown` 等有效状态：此前标为 done，但证据缺失或变更时，不再显示有效完成；此前 in_progress，但执行者状态不能确定时，不能假设仍运行或已经结束。

历史完成记录保留。重新执行时生成新的尝试，不删除过去的问题、结果或取消依据。

### 5.3 必做项和适用性

技能内置要求由版本化规则目录生成，不能靠从计划中删除任务绕过；检查时重新计算适用项及覆盖情况。

简单稿也有计划，但允许合并为较少的工作单元。合并不得丢掉独立的验收条件。编辑模式沿用前置分析豁免；首次环境探测只在环境未验证或变化时适用。豁免依据来自已有任务规则或真实证据，不能用一个任意 `skip: true` 关闭要求。

图表多样性和版式多样性是第 7 节明确的**所有报告固定约束**，不进入按任务模式、篇幅或材料类型过滤的可选要求集合。两条约束必须分别保留、持续显示并独立验收；不能删除、取消、跳过或标为不适用。其他检查的条件豁免不适用于这两条约束。

用户明确的特殊要求进入持久需求记录，保存原要求及可定位来源，并关联落实任务与验收证据。涉及报告内容的具体值仍由 task 或蓝图维护。要求冲突时登记缺口并按现有协议处理，主笔不能自行把用户要求标为不适用。

## 6. 默认 Checklist 与渐进展开

以下是覆盖范围，不要求每个节点永远只对应一个任务：

| 阶段 | 必须覆盖的工作 | 完成证据 |
|---|---|---|
| 需求与计划 | 问题边界、交付要求、工作模式、风险、计划激活 | task、brief、范围与需求记录 |
| 研究与分析 | 关键问题、取证、必要计算、缺口和反证 | 既有 workItems、claims、artifacts、gaps |
| 综合与蓝图 | 核心答案、标题链、每页证明任务 | 当前蓝图及综合校验 |
| 整册表达规划 | 分别检查图表和版式多样性、必要重复与容量 | 当前选型字段及真实规划结论 |
| 前置分析审查 | 作者及必要的独立审查，重大问题修复 | 当前有效 analysis-review |
| 代表页 | 风险页选择、实际预览、关系与阅读路径验证 | 代表页证据和观察；短稿可由全稿覆盖 |
| 整册制作 | 页面/批次制作、内容绑定、局部检查、整册 smoke | 作者片段、装配产物、实际检查结果 |
| 正式工程验收 | 排印检查、acceptance、同版 PDF | 当前 HTML 的检查结果及 acceptance audit |
| 成稿审查 | 双媒介覆盖、全册多样性、来源和推理、告警处置 | 当前实际 review 与问题处置 |
| 返工与复验 | 有问题时自动形成待处理事项，保留传播范围 | 原问题 ID、修复结果和复验 |
| 归档与交付 | 审查快照、打包、最终文件核验和用户说明 | 快照记录、打包回执、最终产物与交付记录 |

蓝图稳定后，可按稳定 slide ID 生成制作任务；不依赖显示页码作为任务身份。批次任务允许用于同一比较组，但完成条件必须能指出其中哪些页面已制作和检查。

多次查询不能重复生成任务。原有任务使用稳定 ID，新增页、删除页和新增问题通过有原因的调整接入。

## 7. 图表与版式多样性的强制落实

### 7.1 所有报告必须包含的两条固定约束

每份报告的 Checklist 必须原义完整地写入并持续显示以下两条，不能弱化成“考虑多样性”“适当丰富”或“按需采用”：

- [ ] **图表多样性：必须尽可能多地使用不同类型的图表。** 每页选型时主动探索适用图表，并从整册角度寻找尚未采用且适配的表达；不能因为少数常用图型已经能表达内容，或因为熟悉、组件现成、制作方便，就停止探索其他适用类型。
- [ ] **版式布局多样性：必须尽可能多地采用不同的版式来组织每一页的内容。** 逐页根据内容选择空间组织、主辅关系与阅读路径，同时统筹整册的布局变化和阅读节奏；不能因为某种布局方便复用，或笼统地以“保持统一”为由反复套用。

建议固定要求 ID 分别为 `chart-diversity` 和 `layout-diversity`。它们适用于 editorial、analytical、exploratory，以及长稿、短稿、新建、修订和内容重排；不得被任务生成器遗漏或被任务合并隐藏。恢复上下文、分派相关子任务和最终交付检查时，必须继续带出这两条约束及当前落实状态。

**“尽可能多”是必须主动追求并接受检查的目标。** 准确性、内容适配和可读性决定采用哪些形式，但不能用来取消探索义务或以“已能表达清楚”提前结束选型。保留重复必须有具体的内容、比较或阅读依据；笼统的“内容适配”“保持统一”不足以通过。

两类要求分别验收；图表丰富不能抵消版式机械重复，反之亦然。阶段任务只记录当前阶段的落实情况，两条固定约束在最终成稿复核通过前不得整体勾选完成；之后若相关内容或布局发生变化，需重新核实当前有效状态。

### 7.2 贯穿规划、制作与验收

| 时点 | 图表检查任务 | 版式检查任务 | 放行依据 |
|---|---|---|---|
| 前置分析审查/ready 前 | 通览证明关系，主动考虑适配形式，解释保留重复 | 通览阅读区域、主辅组织、路径和整册节奏 | 蓝图 `visual.selection/repetitionReason/layoutReason` 等现有字段，以及对当前整册的规划判断 |
| 代表页后、批量制作前 | 实际图形能否呈现预定关系 | 实际空间和阅读路径是否成立 | 代表页实际预览、所见和必要修订 |
| 最终审查 | 按真实编码归并图型，检查机械重复、伪变化和遗漏机会 | 按实际阅读结构核对有效变化，检查正文节奏 | 当前整册 HTML/PDF、具体重复组和问题处置 |

任务必须存在并得到检查。短稿可以在主动探索后得出“同口径比较适合保留同型”的结论，但不能因为页数少而删除或跳过固定约束。文字材料同样必须探索其中可以通过图表表达的比较、结构、机制等关系；实际不存在适用变化时记录具体材料边界及考察依据，不能只凭“文字材料”标为不适用，也不能为勾选编造数据或添加无关图。

完成记录要能回答：查看了哪些页面或比较组；发现哪些适配机会或重复；做了什么调整；哪些重复保留及具体原因；修订后的成稿是否兑现。

继续遵循已有规则：不设统一种数、重复率或逐页备选数量配额；不把组件名称、配色、字号微调当作新图型；不把封面变化当作正文布局丰富；不另建手工逐页图型/布局台账。

**推荐的证据落点：**规划与代表页观察可作为有类型的执行证据保存，引用当前蓝图或预览；最终多样性观察放入原 final review 的条件扩展 `qualityChecks`，计划只引用它。只有启用新 workflow 策略的任务才要求这些扩展字段，旧 review5 保持原规则。

最终 `qualityChecks` 使用两个稳定检查 ID，分别记录真实发现、保留依据、问题处置和对应证据。审查包只预填待查对象，状态为未审；聚合器必须显式保留和校验这些字段，不能在汇总时丢弃。所有按现有 `requiresIndependent` 判定需要独立审查的任务（复杂任务或含重大结论的任务），均要求 author 与 independent 两种角色有整册判断；同一角色多人分工时指定承担整册判断的人，不要求所有成员重复审全册。

最终观察优先引用现有 evidence ID、页面 ID 和当前 audit，避免再存一套截图路径和摘要。快照复制或审查复用时，对新条件字段做明确验证，不能机械继承上一轮整册多样性结论。

脚本验证必需检查存在、范围和证据有效、问题已处置；其通过不等于算法证明“已尽可能多”。

## 8. 执行、委派和上下文恢复协议

### 8.1 更新时点

必须在以下节点持久更新：开始实质工作或委派前；结果接收后；发现阻塞或需要返工时；用户改变要求时；阶段切换时；交接或结束当前回合前。

不依赖“即将压缩”的通知。宿主可能没有该钩子；平时持续保存才是恢复基础。无需为每次查询或无关小操作写日志。

### 8.2 子 Agent 交接

主笔单独维护计划、蓝图和任务绑定。子 Agent 只写独立输出位置，独立审查者自行留下真实审查记录。

每次交接在现有问题、输入、范围、输出、完成条件、不可改条件之外，增加任务 ID、attempt ID、输入摘要和范围版本。返回记录必须说明实际完成范围、产物、限制和采用的输入版本。

主笔接收时检查任务仍然有效、结果对应当前尝试、输入版本可用，再采纳或要求返工。子 Agent 返回“完成”先进入 submitted；工具生成文件也不会自动通过需要判断的验收。

旧需求下的迟到结果保留为候选；不能覆盖当前蓝图，不能重新激活已取消任务。执行者不可用时由主笔继续或重新分派，使用新 attempt ID。

### 8.3 恢复顺序

1. 定位当前报告的 task 和 execution plan。多个候选时明确选择，不以“最新目录”猜测用户所指任务。
2. 读取当前规则、计划版本、任务范围与必需要求；核对绑定和历史修订是否一致。
3. 校验完成证据及当前文件，计算有效状态、失效范围、待答缺口和待接收结果。
4. 对 in_progress 委派查询实际执行者或进程；未知时先核实，不直接完成或重复派工。
5. 读取下一步所需的最少材料，并输出简短恢复摘要，再继续执行。

恢复摘要必须包含任务定位、范围版本、已核实完成、待复核、正在执行/待接收、阻塞和下一步可执行事项。聊天压缩摘要只需保留 task 路径、计划 ID/revision 和重要待答信息，详细状态从磁盘重建。

计划缺失或损坏时，恢复动作只采纳能由有效现有记录证实的状态。不得由聊天回忆补签历史审查。无法恢复的操作标为待核实；可重建当前工作计划，但不宣称补回了真实历史。

重建沿用 task 中的稳定计划 ID，另记恢复事件；保留能读取的损坏原件或历史版本供追溯。不能新建一个无关联计划 ID 来掩盖已丢失的执行历史。

恢复审查身份也不能冒用：新 Agent 不能仅因读到了旧 reviewer ID 就自称同一审查者，继承仍遵循现有审查协议。

## 9. 证据、失效与并发

### 9.1 按信息类型决定完成依据

| 工作类型 | 可接受的完成依据 | 不充分的依据 |
|---|---|---|
| 分析工作 | 当前 workItem 状态、引用与现有分析校验 | 只写“研究完成” |
| 页面制作 | 当前作者片段/装配产物和本项规定的检查 | 只有文件名或空文件 |
| 自动检查 | 实际运行结果、输入摘要、结果文件和成功状态 | 摘抄预期输出 |
| 人工/Agent 判断 | 当前对象、实际所见、结论与处理依据 | 自动 QA 通过或预填 PASS |
| 独立审查 | 实际不同实例、当前证据和满足角色覆盖的原审查 | 主笔更换角色名 |
| 打包交付 | 本轮成功回执、最终输出摘要和文件核验 | 计划里的 done |

机器可证明的步骤可自动标为有效完成；涉及判断的步骤只自动准备待审对象。所有任务状态读取均使用核实后的 effectiveState。

### 9.2 失效传播

输入签名应按任务作用域选择，复用现有分析摘要、页面证据及公共依赖判据。不能把整个计划 revision 当作所有任务的输入签名，否则任意待办变更都会使全计划失效。

| 变更 | 必须重新核实 |
|---|---|
| 任务负责人、备注、待办顺序 | 对应调度信息；不触发报告重审 |
| 单页内容或局部样式 | 受影响页面、相关判断及本轮全册复核 |
| 字体、全局 CSS、画幅 | 按既有公共依赖规则扩大视觉复核范围 |
| 核心假设、模型、来源或标题主张 | 受影响分析、综合判断、前置及成稿审查 |
| 新增/删除页面或重要要求 | 更新覆盖清单、整册规划及相关全局检查 |
| 无法判断影响范围 | 标为待核实，保守扩大检查；不沿用未经确认的 PASS |

分析工作项的原有状态本来就在分析摘要中，这一行为不修改。新增计划引用其结果；不会为了减少重审而改动 `semantic-v2` 的既有投影。

### 9.3 写入与中断恢复

复用任务锁，计划更新使用 `expectedRevision` 防止旧上下文覆盖新状态。每次转换先验证依赖、适用项、证据与前置 revision，再写完整新版本，最后原子替换当前计划。

历史计划保存在 revisions 中，只读不覆盖。写入完成但尚未发布的版本不算当前状态；失败保留诊断，上一有效版本继续可用。派生 progress.md 生成失败不使计划写入失效，下次重新生成即可。

生产命令和状态接收共用同一个任务锁边界，避免嵌套加锁；实现时可提取现有事务辅助模块。确定性成功回执可帮助恢复“输出已产生、计划尚未更新”的中断，但须校验输入与输出后才能补记。

明确以计划当前版本的原子替换作为计划提交点。若提交后写 latest 索引或派生视图失败，返回“计划已提交、辅助发布失败”及实际 revision，不误报为完全未写入，也不让调用者重复应用同一次变更。变更携带 operation ID，重试需要幂等处理。

### 9.4 统一路径和锁归属

- 原始或派生 task 的 `executionPlan.record` 相对该 task 文件；经 `readAnalysisTask` 回绑后相对蓝图；HTML 内嵌合同中的 record 相对 HTML；plan 内部记录相对 plan 文件。
- QA 没有 task 参数时，从 HTML 的内嵌合同解析计划；不使用 cwd 或 audit 目录猜测其位置。`load`、派生 task 与分析回绑调用统一解析函数。
- 新工作流的锁归属由解析后的计划根目录确定，根 task、派生 task、独立输出 HTML 和直接 CLI 必须落到同一把任务锁。
- 当前 `report qa` 在持锁时以子进程启动 `qa_deck`。推荐将 QA 执行主体提取为同进程可调用函数：统一入口传入内部事务上下文，直接 CLI 则自行获得同一把锁。不能让子进程再次抢同一把锁，也不能公开一个可跳过门禁的 `--skip-lock` 参数。
- 只读状态查询读取完整已发布版本，不写锁状态；正式生产门禁与操作在同一写事务内核实当前 revision 和输入，并在成功接收时再次核对必要摘要。

## 10. 命令与门禁设计

### 10.1 推荐接口

扩展统一 `report.cjs`，不用另造一套命令体系。以下为接口草案，参数细节在实施时定稿：

```text
report init <新目录>
report plan <task.json>                      读取计划、有效状态与要求覆盖
report plan <task.json> --activate <方案文件> 激活或细化当前计划
report plan <task.json> --update <变更文件>   按 expectedRevision 原子更新
report plan <task.json> --recover <记录清单> 显式重建可证实状态，保留恢复依据
report status <task.json> [...]              原门禁 + 执行进度，分开显示
report next <task.json> [...]                可执行项、待接收项、阻塞及优先建议
report resume <task.json>                    只读核实并输出恢复摘要
```

状态转换、结果接收和委派由有类型的变更操作表达；CLI 不接受任意写 done 绕过完成条件。既有宿主 Todo/Plan 工具可以作为展示镜像，落盘记录仍是统一依据；不要求某一种宿主 API 才能运行技能。

`status` 和 `resume` 保持只读，不自动签署、执行任务或修复计划。需要持久调整时走 plan update。终端工具本身也不伪装成能够查询宿主子 Agent：恢复摘要提示需查询的 ID，由主 Agent 使用真实工具核实后更新。

保留原门禁结果字段，新增独立 execution 结果。CHECKED 仍只表示既有指定记录有效，不能改名成为“项目全部完成”。`next` 不只返回固定链的第一个失败项，也应列出可以并行推进的无阻塞工作。

对新 workflow 任务，从已核实的 `productionRefs` 定位当前派生 task/audit/review 后执行生产状态检查，并在输出中同时展示原任务路径与实际所检版本；无有效引用时明确缺失。旧任务继续支持原来的显式参数行为，不自动扫描目录。

用户可见进度示例（仅示意）：

```text
当前阶段：整册制作，计划 revision 12
已核实：分析审查、图表规划、版式规划、3张代表页
正在执行：制作正文 S07–S09
待接收：行业研究补充结果，attempt 2
阻塞：内部成本数据待答，仅影响估值分支
待复核：S04来源变化，需重新核实相关判断
下一步：先接收研究结果；成本未到时继续制作无依赖页面
交付还差：整册验收、双媒介审查、图表/版式最终复核、打包
```

进度以当前工作、剩余范围和阻塞为主。可以展示“当前清单已完成 N/M 项”，但必须明确它不是工时完成百分比；动态新增任务后分母可以变化。

### 10.2 分阶段检查，避免循环依赖

| 边界 | 必需状态 | 此时不能要求已完成的后续工作 |
|---|---|---|
| 正式 ready / compile | 计划已激活，当前页面职责已登记，图表/布局规划已核实，原前置审查满足 | 代表页、全稿、最终审查 |
| 全稿 acceptance | 制作范围覆盖完整，代表页阶段已完成，必要制作检查与排印检查有当前证据 | 最终双媒介审查、打包 |
| 最终审查聚合 | 当前审查满足原规则及新策略的多样性观察要求 | 打包、交付说明 |
| 正式 package | 所有适用的交付前任务有效完成，当前 audit/review 有效 | 本次打包成功及后置交付任务 |
| 任务关闭 | 打包结果核实、归档要求完成、对用户交付已记录，必要未决项如实披露 | 不适用项以及已明确取消的工作 |

代表页必须先于批量制作是 Agent 执行协议；工具在正式验收边界核对其证据。不能宣称仅凭事后文件存在，就证明作者确实按先后顺序工作。

工程硬门禁调用共用 `assertGate()`，同时接入正式底层 CLI 和统一入口，防止只绕过 `report.cjs` 就跳过执行计划。至少覆盖 ready/compile、acceptance 和 package 的正式路径。

不要把实时计划校验塞入所有 `analysis_contract.validate()`、`verifyPlan()` 或历史 review 验证路径。历史审查和快照验证只核实所绑定内容；实时进度检查仅在明确的当前生产边界调用。

预览仍可用于研究或制作尝试，必须保留预览身份。预览豁免不允许生成正式交付，也不免除来源、算术和真实分析等既有底线。

### 10.3 打包、归档和关闭的无循环顺序

1. 核实交付前任务，冻结本次输入计划版本 `Pn`。
2. 对当前 HTML/PDF/audit/review 执行正式打包。
3. 生成回执 `R`，绑定 `Pn` 的摘要、输入审查摘要及输出 HTML/PDF 摘要。
4. 发布 `Pn+1`，本次打包任务的完成证据引用 `R`。回执不引用 `Pn+1`，避免相互摘要依赖。
5. 保存执行归档，发送交付说明；后置完成由后续计划版本或外层运行记录证明。

审查快照可以在打包前完成。它保存已完成的审查事实；进行中执行计划可作为独立 checkpoint 附件。完整执行归档在打包后保存，明确区分 checkpoint 与 complete，不能让归档中仍有后置任务就否定已有效的历史审查。

工作流附件使用独立 manifest/schema，保存计划、回执和恢复必要的内部文件，核对摘要与可迁移引用；不改已有 snapshot manifest1 的含义。任务恢复归档不能只保存一个 plan，而遗漏其引用的委派结果、局部制作文件和必要上下文；审查快照仍不宣称替代所有可编辑底稿。

“最终消息已经发送”只能在宿主确实可获得发送事实时补记；否则最后一版计划保留待回执状态，之后恢复时根据真实对话记录确认。不能为得到全绿清单提前伪记交付。

## 11. 版本与旧任务兼容

推荐维持 blueprint3 / task3 / pages4 / analysis-review2 / final-review5，新增显式可选策略槽：

```json
{
  "policyVersions": {
    "analysis": "semantic-v2",
    "reading": "reading-shadow-1",
    "visual": "structural-lines-1",
    "references": "single-page-1",
    "workflow": "execution-plan-1"
  }
}
```

选择第五策略槽的原因：当前旧运行时要求严格四槽，会拒绝带新 workflow 的任务；新运行时可以同时识别原四槽和明确的五槽。新要求不能被旧运行时静默忽略，也无需为执行状态引入 task4 并改动大量 `version === 3` 的既有分支。

实施规则：

- 保持已有 `DEFAULT_POLICIES` 的四槽解释；不得因为运行时升级给旧 task 自动补 workflow。
- 新能力在 `contract_capabilities` 集中查询，未知 workflow 明确拒绝。
- 新 init 在正式启用后默认生成新策略、稳定计划绑定和计划骨架；原视觉候选策略的默认选择不随本升级改变。
- 历史 task1/2/3、旧审查和旧快照按原合同读取。状态视图明确说明该任务未启用执行计划，不能报告“已满足新工作流”。
- 旧任务可显式建立恢复计划；若升级为新正式工作流合同，应在新目录生成副本，保留原字节和审查记录。只采纳能证实的既有完成情况，缺失的规划/判断不得补签。
- 首次加入 workflow 策略改变公共依赖，已有任务需按实际合同重新验收。此后只改计划进度不影响分析摘要和视觉证据。

这次对策略槽的扩展需要更新维护文档，并测试审查聚合对新条件字段的保留。不能只给 normalizer 多加一个可忽略字段。

| `review_pack.cjs` / `aggregate_reviews.cjs` / `review_contract.cjs` | 新 workflow 条件下多样性检查草稿、实际记录、聚合与验证 |
| `snapshot_review.cjs` 及执行归档辅助 | 独立保存工作流附件，不将实时 plan 加入已签 taskRecords |
| `docs/maintainer-contracts.md`、生产入口文档、README | 新旧行为、能力边界、迁移与用法 |
| tests / evals | 下述工程不变量和跨上下文行为验证 |

当前 `check_units.cjs` 是独立命令。执行计划至少必须调度并记录该检查，绑定所检查 HTML。是否进一步并入 QA 可由实现选择，但不能仅因 acceptance 通过就自动勾选排印检查。

## 13. 实施分期与每期出口

| 阶段 | 交付内容 | 出口标准 |
|---|---|---|
| A：持久计划与恢复 | 模型、稳定 ID、规则目录、原子更新、plan/status/next/resume、委派接收、视图 | 可中断并恢复；能发现过期结果与失效证据；同一信息不双写 |
| B：强制要求与生产接入 | 多样性规划/代表页/成稿任务、条件 review 字段、底层阶段门禁、打包回执 | 删除任务、手改 done、绕开统一入口都不能得到符合新合同的正式交付 |
| C：兼容、归档与迁移 | 四/五槽兼容、locator 归一化、历史审查隔离、执行归档和显式升级 | 旧记录解释不变；普通待办更新不引起重渲染或重签；归档可迁移核实 |
| D：真实行为试运行与启用 | 不同模式报告、上下文交接、委派/返工场景的独立实跑 | 下述行为底线满足后，候选能力切换为新任务默认 |

分期是实施顺序，不表示 A 完成就可以宣称“强制 Checklist 已交付”。用户要求的完整能力需要 A–D 全部达到出口标准。

不预先承诺固定工期或提速比例。记录额外计划操作、恢复耗时、无效重做和返工原因，用实际试运行评估成本。最小版不建设后台服务、进度看板应用、自动排期器或复杂分布式调度系统。

## 14. 验收与发布底线

### 14.1 工程验收

1. 新任务生成计划骨架，缺失或未激活计划不能进入新合同的正式生产。
2. 编辑、分析、探索三种模式生成正确适用项；编辑前置审查豁免不被误拦截。
3. 必需项删除、遗漏需求覆盖、依赖循环、无效对象引用被拒绝。
4. done 声明缺少当前证据时无效；有文件但无实际审查不能放行视觉任务。
5. 旧 revision 更新被拒绝；并发返回不会丢失任务或覆盖新状态。
6. 写入中断保留上一有效状态；输出成功而进度未发布时可凭有效回执恢复。
7. 过期 attempt、过期范围和已取消任务的迟到结果不能自动接收。
8. 只改计划状态或定位路径，不改变分析摘要或视觉依赖；计划真实要求变更仍按作用域触发复核。
9. 单页变更、全局 CSS 变更、分析假设变更分别产生正确失效范围。
10. 直接调用正式 compile/ready、acceptance、package 与统一入口使用相同工作流门禁。
11. 预览、smoke 和不完整双媒介审查不能被计划的 done 转换为正式交付。
12. 打包前无需打包任务已完成；回执链无自引用，失败不预标完成。
13. 新策略 review 的质量检查经过聚合仍完整；缺少必要角色的整册判断被拒绝，明确覆盖 `simple + majorConclusion=true` 组合。
14. 四槽旧任务原样读取；旧运行时拒绝五槽新任务；未知 workflow 拒绝。
15. 历史快照无需读取活计划；工作流归档复制到新目录后仍能验证。
16. 完成数只是当前任务计数；新增任务后变化不伪称工时进度，取消不算完成。
17. 原 task 与派生 task 正确关联；过期 compile/audit 不能因 latest 或 plan 中的定位而成为当前版本，直接 CLI 结果需校验后接收。
18. 根 task 始终未被改写时，完成 compile→assemble→QA 后只传根 task 仍能恢复当前有效链；失败新运行不覆盖它。
19. 不同 cwd、根/派生 task、独立输出 HTML 和直接 CLI 的计划解析一致；QA/package 与计划更新互斥，统一入口 QA 不发生嵌套锁失败。
20. 所有模式、篇幅和材料类型的 Checklist 均保留 `chart-diversity` 与 `layout-diversity` 两条固定约束；删除、取消、跳过、标为不适用或合并隐藏均被拒绝。恢复与相关委派继续携带原义完整的约束，最终完成须分别关联当前成稿检查证据。

### 14.2 Agent 行为验证

选择一个短编辑稿、一个定量分析稿、一个存在未决缺口的探索稿；至少一例需要独立审查。使用相同材料和可比执行条件，比较当前技能与候选技能；不把工程测试通过当作行为改善证据。

在真实或明确标注的模拟交接点切断原上下文，把当前用户请求、技能入口、任务路径和可用宿主状态交给新实例，不提供隐藏答案。重点覆盖：

| 场景 | 期望行为 |
|---|---|
| 研究尚未形成页面时恢复 | 恢复问题、缺口和可执行研究，不要求先补造完整蓝图 |
| 子 Agent 已交稿、主笔未接收时恢复 | 发现 submitted，核对后接收，不因文件存在自动完成 |
| 两个 Agent 返回且一个输入已过期 | 接收有效结果，隔离过期候选 |
| 原执行者仍运行或状态未知 | 查询或明确待核实，不盲目重复派工 |
| 用户改变范围并取消某分支 | 调整计划、保留原因，旧结果不能重启取消工作 |
| 代表页失败 | 形成有传播范围的返工，不能继续机械批量制作 |
| 图表组件换名字或布局只换颜色 | 不承认有效多样性变化 |
| 同口径地区比较需要重复 | 保留有依据的一致性，不为数量强行换图 |
| 短稿、编辑稿或文字材料试图省略多样性要求 | 两条固定约束仍在，必须主动探索并留下具体依据；不接受“不适用”或笼统的“保持统一” |
| 自动 QA 通过但未查看 PDF | 最终视觉与交付仍未完成 |
| 局部修改后复用草稿无 pendingPages | 仍核实本轮全局判断和新策略要求 |
| 完成后文件被删除或改动 | 恢复时显示失效，不沿用全绿清单 |
| 计划缺失 | 只重建有依据的状态，不补签过去的认知工作 |

必须通过的发布底线：必需要求没有遗漏；没有未发生工作的假完成；旧证据不会覆盖当前版本；恢复后能给出有依据的下一步；新旧合同不串用。记录重复执行次数、恢复偏差、额外操作与耗时，以判断计划维护是否过重；未经测量不设改善百分比。

## 15. 推荐决策

推荐实施 **“独立持久计划 + 现有证据派生状态 + 阶段强制门禁 + 恢复协议”** 的完整方案，并在验证后对新任务默认启用。

只在 SKILL.md 增加“先列 Todo、随时更新”的文字，开发成本最低，但不能可靠处理压缩恢复、过期结果和假完成，可作为早期试验，不满足本次完整目标。

本方案的额外成本集中在状态和证据接入、兼容验证及真实行为测试。通过引用现有真源、渐进细化任务、派生进度视图和机器可核验步骤自动记账控制维护量。实施之前需要用户决定是否采用这套完整机制；具体文件名和参数细节属于实现中的常规选择。
